### A4 Sorting comparison

For `appointments.sort(key=appointment_sort_key)` and `result = sorted(appointments, key=appointment_sort_key)`, predict source order, return value and result identity. Give a meaningful mutation check: [Calling appointments.sort(key=appointment_sort_key) changes the order of the original appointments list in place and returns None. The variable still refers to the same list object, however its order has been mutated. In contrast, result = sorted(appointments, key=appointment_sort_key) leaves the source appointments list unchanged and returns a new list object containing the same Appointment object references in sorted order. A meaningful mutation check is to save the original source order, for example the sequence of appointment IDs, call the query and then assert that the source order is exactly unchanged. Checking only the list length would not detect reordering.]

Score-example prediction and explanation of passing the named key: [For scores = [(Bea, 8), (Ali, 8), (Chen, 5)], sorted(scores, key=score_key) produces [(Chen, 5), (Ali, 8), (Bea, 8)]. The function returns (score, name), so sorting first uses the numeric score and then the name to break equal-score ties. Passing score_key as key=score_key gives sorted() the function itself so Python can call it once for each item. Writing key=score_key() would incorrectly call the function immediately without supplying the required item. The same principle applies to appointment_sort_key, which should be passed as a function so each Appointment can be ordered by its date/time and then appointment ID.]

Explain cancellation versus deletion, and checks for same-session lookup, all-status listing and SCHEDULED-only exclusion: [Cancellation changes the status of the existing Appointment object from SCHEDULED to CANCELLED rather than deleting it, since SmartCare must retain appointment history during the current session. To demonstrate this, the cancelled appointment should still be returned by find_appointment() as the same stored object and listing that practitioner's appointments with no status filter should still include it. In contrast, listing with AppointmentStatus.SCHEDULED should exclude the cancelled appointment since its current status is no longer SCHEDULED. Responsibility check: explain how domain invariants, shared-store collections, service coordination, pure queries and console effects remain separate: [Domain classes retain entity state and invariants such as appointment cancellation rules. SmartCareDataStore owns the shared session collections and provides lookup and list operations while preserving stored object identity. ## G. Ten formative answers

1. What makes select_appointments pure, and what side effect breaks purity? [select_appointments is pure because it produces the same result for the same explicit inputs and does not change external state. Modifying global variables, changing appointment statuses, performing input/output, or altering the supplied collection would break this purity.]
2. Which explicit inputs are needed, and why avoid a global store? [The function needs the appointment collection, practitioner ID and optional status filter as explicit inputs. A global store should be avoided because hidden dependencies make the function harder to test, reuse and understand.]
3. How can a new list reuse Appointment objects safely? [A new result list can contain references to the same Appointment objects without modifying them. The list container is separate, but the appointment objects inside it are shared. This preserves object identity while allowing filtering and sorting without changing the original list.]
4. Why use a named key, and what breaks equal-time ties? [A named sorting key makes the ordering rule easier to understand, test and maintain. Appointments are first ordered by date_time, and when two appointments have the same time, appointment_id provides the tie-break.]
5. How do default and explicit status filters differ? [When the status argument is None, appointments of all statuses are included. When an explicit AppointmentStatus value is supplied, only appointments with that status are returned.]
6. How do empty, unknown practitioner and invalid filter cases differ? [An empty result means the request was valid and the practitioner exists, but no appointments matched. An unknown practitioner means the supplied valid practitioner ID is not registered and should raise LookupError. An invalid filter, such as a non-AppointmentStatus value, should raise ValueError.]
7. Which console errors recover, and how is unchanged state checked? [Recoverable console errors include invalid dates, unknown menu choices, blank or unknown IDs, duplicate registrations, invalid status filters and invalid appointment operations. The system should report the error and continue the menu. State can be checked by confirming that valid records remain unchanged and that rejected operations did not create or modify records.]
8. What is data integrity for registered participants, conflicts and history? [Data integrity means appointments reference registered patient and practitioner objects, scheduling conflicts are prevented for the same practitioner at the same date and time while scheduled, and cancelled appointments remain in the current session as history rather than being deleted. Stage 9 does not persist this information after the program exits.]
9. What is Copilot's review role, and who verifies findings? [GitHub Copilot can assist by reviewing the implementation, identifying possible defects or missing tests, and suggesting improvements. The developer remains responsible for checking whether those findings are correct and deciding whether any changes should be made.]
10. How do pure functions and OOP responsibilities work together? [Pure functions handle operations such as filtering and sorting without changing external state, while domain objects represent entities and maintain their own state and rules. Services coordinate application operations, the data store manages session collections, and the console handles user input and output. This keeps responsibilities separated across the system.]
